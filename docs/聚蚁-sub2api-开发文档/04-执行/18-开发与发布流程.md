# 18 开发与发布流程

## 本地开发

- 默认工作分支是 `custom`；`main` 只作上游镜像参考，`upstream` 只读。
- 聚蚁能力优先新增文件，修改上游文件前先确认最小插入点。
- 前端不加聚蚁专用 npm 依赖；使用现有栈或 vendored assets。
- 未经用户明确要求，不推送、不部署、不操作生产。

## 上游 release 同步

1. `git fetch upstream --tags --prune`，通过 GitHub release 或语义版本排序确认最新正式 tag。
2. 验证 tag object、peeled commit 和当前 `custom` 的祖先关系；已经合入则不制造空 merge。
3. 未合入时在 `custom` 执行 `git merge --no-ff <tag>`。
4. 冲突按当前 51 文件净差异审计：品牌/功能改动保留 ours；历史残留取 tag；双方新增 import 必须合并语义。
5. `setting_handler_update.go` 手工保留 `ext:` 绝对 HTTP(S) 验证。
6. 运行前端 build、相关 Vitest 与后端定向测试。
7. 推送时先推 tag，再推 `custom`，避免 CI `git describe` 读到旧版本。

## CI 镜像

`custom-build.yml` 对 push、定时和手动事件统一产出：

- `custom-<sha8>`：不可变，唯一允许用于生产。
- `v<version>-custom`：版本别名，用于发现与对账。
- `custom-latest`：移动标签，只供开发/发现，生产禁用。

CI 的触发 `head_sha` 可能是同步前提交；镜像标签应以 build 后的 `sha8` 和 GHCR versions 为准。

## 生产四连

```bash
/opt/sub2api-tool/update-from-ghcr.sh pull  custom-<sha8>
/opt/sub2api-tool/update-from-ghcr.sh smoke custom-<sha8>
bash /root/sub2api-deploy/backup.sh
/opt/sub2api-tool/update-from-ghcr.sh switch custom-<sha8>
```

硬门：

- smoke 的 PG/Redis 是临时实例，不挂生产卷。
- `/health`、实际版本和聚蚁 `logo.svg` marker 全过。
- 备份存在、非空并通过 gzip 完整性检查。
- switch 后检查内部 8181、公网 443、容器健康、公开设置、关键日志和真实浏览器 console。
- 验收后执行 `smoke-down`。

## 回滚

`update-from-ghcr.sh rollback` 在 current 与 previous-image 间切换。跨版本回滚前先查看迁移：若旧二进制不能读取新 schema，不能只换镜像；应停机评估并使用已验证备份恢复。管理台内置更新/回滚入口永远禁用。
