# M3-T1　维护面板认证、OAuth 与身份绑定

- 所属模块：[[M3]]　身份、授权与安全：密码/OAuth/Passkey/2FA/JWT、API Key、ACL、限流、step-up 与审计边界
- 前置依赖：[[M1-T2]]、[[M2-T2]]
- 完成后解锁：[[M3-T2]]、[[M10-T1]]、[[M14-T2]]

## 输入 / 产出

- **输入**：登录/OAuth/Passkey/2FA 请求
- **产出**：用户 session、身份绑定和审计事件

## 验收标准

> 逐条都要满足，这是验收时的唯一依据。

1) 高风险入口限流故障时 fail-close（[[E-05]]）
2) 并发 identity/email/alias 只允许一次成功（[[E-06]]）
3) refresh/logout/revoke 能撤销 session

## 必须处理的边界

- [[E-05]]　高风险认证限流无法判定
    - 触发：Redis 故障或限流状态读取失败
    - 期望：登录、注册、2FA、refresh、OAuth start 等入口 fail-close，不放大攻击面
- [[E-06]]　身份或邮箱并发绑定
    - 触发：两个请求同时绑定同一 identity、email 或 alias
    - 期望：事务与唯一约束只允许一个成功，另一个返回冲突，不生成重复用户/绑定

## 代码位置

<!-- code:begin -->
- `backend/internal/server/routes/auth.go` — 认证路由、审计和 fail-close 限流（E-05）
- `backend/internal/handler/auth_handler.go` — 登录、注册和 session HTTP 编排
- `backend/internal/service/auth_service.go` — 密码、token 与用户认证
- `backend/internal/service/auth_email_binding.go` — email/alias 事务绑定（E-06）
- `backend/internal/service/passkey.go` — Passkey 注册与登录
<!-- code:end -->

## 实施沉淀

<!-- notes:begin -->
高风险认证限流在 Redis 不可判定时拒绝请求，这是有意的安全可用性取舍。Identity/email/alias 的最终竞争由事务与唯一约束裁决；callback 层不得先创建用户再尝试补绑定，否则并发会留下孤立身份。
<!-- notes:end -->
