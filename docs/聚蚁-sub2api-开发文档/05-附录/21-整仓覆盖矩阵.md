# 21 整仓覆盖矩阵

## 覆盖口径

“整仓进入知识库”不等于把 3,717 个 tracked files 复制成 3,717 篇笔记。这里采用两层覆盖：

1. 每个稳定职责域都有模块、维护任务、边界和少量高价值代码入口。
2. `_run/check_coverage.py` 给每个 tracked file 指定一个主要维护模块；上游新增文件未匹配规则时检查直接失败。

一个文件可能跨多个模块，例如 `server/routes/admin.go` 同时注册身份、账号、支付、Ops、插件和运营路由。覆盖脚本只记录主要结构所有者；真实依赖仍以第 06/17 节和任务代码位置为准。

## 提及级覆盖口径

归属检查之外，还有一层“提及级”审计：解析全部受保护 code blocks，确认每个稳定职责域都有可导航入口。以 `custom` 基线实测：

- 首轮提及盲区 1,170 个文件；按子系统补入目录级/家族代表条目后降至 100 个。
- 剩余 100 个中约四成是共址测试（`*_test.go`，与实现同目录，归 M15 约定），其余为单文件助手或治理/构建配置，均已在同家族条目的描述中点名（如验证码三件套、影子凭据、goreleaser 配置族）。
- 策划原则：多文件家族和独立能力必须有精确条目；单文件助手靠家族条目描述导舂，不为它们逐条建行——否则模块笔记会退化成文件索引。

上游合并后运行一次第 22 节的两个检查脚本，再抽查 `图谱/模块/` 的代码位置，即可发现新出现的未纳管域。

## 自动检查

```bash
python3 docs/聚蚁-sub2api-开发文档/_run/check_coverage.py --root . --check
```

通过条件：

- 第 06 节中存在脚本引用的全部模块。
- 除 vault 自身外，每个 `git ls-files` 结果都得到一个主要模块。
- 未定义模块和未归属路径均为 0。

新增目录或稳定业务域时，不能只给检查器增加 fallback：先判断是否需要新模块/任务/边界，再更新覆盖规则和本矩阵。
